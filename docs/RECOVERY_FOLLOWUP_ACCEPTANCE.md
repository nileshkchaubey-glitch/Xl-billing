## Supported recovery and limitations

Standalone recovery validates the selected candidate using the same schema and accounting rules before any mutation. It accepts historical opening receipts and supplier discounts supported by those rules, and rejects ambiguous or inconsistent candidate histories without rewriting their bytes. Missing, default-only, corrupt or unreadable current PIN credentials cannot authorize locked changes. Such profiles retain raw export for review; importing a new credential never substitutes for current-owner verification.

The raw export preserves exact captured records, metadata and journal, including malformed bytes. Re-selection proves possession of matching exported contents. It does not prove physical disk durability, file location, independent hardware or later availability. Owners must retain that private file outside the browser profile; it contains settings and credentials.

A captured current profile is reliable evidence of the bytes being reviewed. It is not an earlier committed historical snapshot. Restore differences are reported only when both captured current records and the selected candidate fully validate. Otherwise the preview shows unavailable before counts/differences and preserves the captured raw archive. A valid backup can replace an archived corrupt current profile only after the complete review, current PIN and explicit owner choice.

localStorage has no transaction across multiple keys. Recovery uses checked before/after evidence and a retained journal; it cannot promise physical durability against eviction, device loss or power failure. Older app copies can ignore cooperative locks. Unsupported locking leaves mutation unavailable; export remains the safe path. Native mobile folder support and real printers are separate limitations, not passed claims.
